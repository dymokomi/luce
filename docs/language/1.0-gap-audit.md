# Luce 1.0 Language-Gap Audit

## Language machinery needed for the operating system and behavior platform

Status: design audit and roadmap input. [Luce 1.0](1.0.md) remains the
authoritative specification until individual proposals pass their design,
implementation, and corpus gates.

## 1. Why this audit exists

The current Luce 1.0 design is shaped around two proving programs: the Luce
compiler and serious native applications. The wider project adds several more:

- the operating-system kernel and runtime;
- drivers, graphics, networking, and media systems;
- capability-scoped behaviors operating on durable information;
- safe composition by domain authors, people, and AI agents;
- execution across workers, devices, and independently governed communities.

This wider proving corpus changes the feature-placement calculation. The
question for each requirement is:

> Can an ordinary Luce package implement and enforce this property for its
> users?

A capability belongs below the library boundary when it must:

- alter copy, ownership, destruction, or escape semantics;
- define the machine memory model or calling convention;
- prove a property transitively across calls;
- participate in control-flow lowering;
- expose canonical declaration facts available only to the compiler.

The audit identifies five language-semantic gaps and three compiler-product
gaps. Four of the language gaps introduce potential source surface. The rest can
use compiler-known APIs, product metadata, analysis, and tooling.

## 2. Summary

| Gap | Why a library cannot enforce it | Proposed disposition |
| --- | --- | --- |
| Owned and affine values | A library cannot prevent copies, aliases, use after transfer, or duplicate consumption | Add a narrow opt-in facility to 1.0 |
| General scoped values | A library cannot prevent return, storage, capture, or transfer beyond a lexical authority boundary | Generalize the existing escape checker in 1.0 |
| Restricted const generics | A library cannot define families whose layout and type identity depend on compile-time values | Add restricted constant parameters to 1.0 |
| Fallible iteration | A library cannot integrate item/end/error with `for` and explicit propagation | Resolve before `for` lowering is frozen |
| System memory and execution substrate | Atomic ordering, volatile access, alignment, and interrupt ABIs require backend semantics | Add a closed system profile to the language/compiler contract |
| Flow-sensitive refinement | Packages cannot prove or invalidate branch-local facts for the compiler | Add to semantic analysis |
| Execution profiles and operational contracts | Retry, allocation, blocking, determinism, and native reachability require transitive analysis | Add to product checking and compiler summaries |
| Canonical declaration descriptors | Runtime libraries cannot inspect arbitrary declarations when reflection is absent | Add a versioned compiler query and artifact |

## 3. Owned values and consuming transfer

### The pressure

ARC provides approachable shared identity for applications and long-lived object
graphs. Some important values represent exclusive ownership:

- files, sockets, mappings, and device handles;
- GPU command buffers and submission tokens;
- exclusive capabilities and leases;
- large buffers transferred between execution domains;
- native objects with move-only ownership;
- intents whose authority may be consumed once.

An ARC wrapper can represent these values through a mutable `closed`, `valid`,
or `transferred` flag. Every alias remains capable of calling the wrapper, so
invalid use becomes a runtime state check. Strong cycles can also delay final
release.

### The semantic requirement

Luce needs an opt-in category of noncopyable values with consuming transfer:

- an ordinary assignment or consuming call transfers ownership;
- a transferred binding becomes unavailable;
- every live value has at most one owning path;
- leaving scope runs deterministic destruction;
- an explicit fallible `close` operation remains possible;
- ordinary structs and enums retain value-copy semantics;
- ordinary classes retain ARC identity semantics;
- no named lifetime parameters enter user code.

Conceptually:

```luce
owned File

func publish(file: take File) -> Receipt!:
    # The caller's ownership enters this function.
```

The syntax is still open. The initial work should specify state transitions and
diagnostics before selecting keywords.

### Interaction with failure and destruction

A consuming operation may fail after ownership has entered the callee. Its
contract must make the resulting ownership state unambiguous. Useful patterns
include:

- consumption succeeds or automatic destruction occurs inside the callee;
- failure returns the owner alongside the error when retry is meaningful;
- a consuming fallible `close` releases the resource and reports shutdown
  errors;
- traps invoke the host's containment and forced-cleanup policy.

Destruction itself remains non-fallible. Error-aware shutdown stays explicit.

### What this unlocks

- statically safe move-only native wrappers;
- exclusive capability tokens;
- zero-copy transfer of unique buffers to workers;
- command builders with one final submission;
- clearer resource shutdown and invalidation;
- measurable ownership at system boundaries.

### Acceptance gate

Implement representative file, socket, GPU-command, unique-buffer, and
single-use-intent types. The compiler must reject aliasing and use-after-transfer
programs, run destruction exactly once on every ordinary/fallible exit, and
preserve the same behavior through the HIR interpreter, MIR interpreter, and
compiled backends.

## 4. General scoped values

### The pressure

Luce already gives special escape behavior to two types:

- `mutable_slice[T]` is callback-scoped and non-storable;
- `task[T]` is confined to its structured task lifetime.

Native borrows, callback tokens, behavior contexts, transaction builders,
temporary capabilities, and arena access create the same underlying problem.
Adding another compiler-special type for each domain would enlarge the privilege
ledger and prevent packages from building equally safe abstractions.

### The semantic requirement

A scoped value may flow through calls inside its lexical region and may not
escape that region. The compiler rejects:

- returning it;
- storing it in longer-lived state;
- capturing it in an escaping closure;
- sending it to another worker;
- erasing it inside an unrestricted interface value;
- embedding it in an unrestricted value that outlives the region.

Conceptually:

```luce
scoped struct WorldAccess:
    let photos: ReadCapability
    let drafts: WriteCapability

func create_film(context: scoped WorldAccess) -> FilmPatch!:
    # Access is valid for this invocation and its nested calls.
```

The compiler infers lexical origins. Users do not name or compare lifetimes.
Passing a scoped value to another scoped parameter remains ordinary.

### Relationship to owned values

Owned and scoped solve complementary problems:

- **Owned** answers who has the unique responsibility for a value.
- **Scoped** answers how far temporary access may travel.

A non-consuming method can receive call-scoped access to an owned value. A
consuming parameter receives ownership itself. This small combination provides
most resource and capability patterns while preserving ARC as the ordinary
application model.

### What this unlocks

- package-defined temporary mutable views;
- behavior contexts with invocation-bounded authority;
- safe transaction builders;
- arena and pool access without stale references;
- foreign borrows with compiler-enforced escape rules;
- one implementation mechanism for mutable slices and structured task handles.

### Acceptance gate

Replace the existing mutable-slice and task escape special cases with the shared
analysis. Compile packages that define their own scoped view and capability
types. Diagnostics must identify the exact storage, closure, return, interface,
or worker path that would cause an escape.

## 5. Restricted const generics

### The pressure

The built-in `array[T, N]` accepts a compile-time size. User-defined generic
types accept only type parameters. This prevents packages from expressing
families such as:

```luce
FixedBuffer[u8, 4096]
Matrix[f32, 4, 4]
Packet[Header, 128]
RingBuffer[Event, 1024]
BitSet[256]
Vector[f32, 8]
```

These are common in protocols, media, graphics, numerical work, drivers, and
bounded runtime structures. Their size participates in layout and type identity,
so an ordinary library implementation cannot recover the missing parameter.

### The semantic requirement

Add a restricted compile-time constant parameter, conceptually:

```luce
struct FixedBuffer[T, const capacity: u64]:
    var data: array[T, capacity]
```

The first version should allow:

- integer and Boolean parameters;
- enum constants if they prove useful;
- the existing restricted constant-expression language;
- use in array lengths, type identity, bounds, and constant calculations;
- inference from argument types where unambiguous;
- explicit monomorphization and expansion budgets.

It should exclude:

- arbitrary user-code execution at compile time;
- heap allocation during constant evaluation;
- dependent propositions and proof terms;
- unbounded recursion or package-controlled compiler plugins.

### What this unlocks

- package-defined fixed storage;
- safer wire and device layouts;
- reusable SIMD, matrix, and tensor foundations;
- bounded queues and caches;
- fewer compiler-only generic exceptions.

### Acceptance gate

Implement fixed buffer, matrix, packet, and ring-buffer examples. Verify type
identity, layout, inference, separate compilation, diagnostics, monomorphization
budgets, and backend agreement. The feature succeeds when `array[T, N]` can be
explained as an ordinary use of the same constant-parameter mechanism.

## 6. Fallible iteration

### The pressure

The current iterator protocol returns `T?`, which represents an item or normal
exhaustion. Many system and world operations have three outcomes:

- an item;
- normal completion;
- an operational error.

Examples include directory enumeration, network streams, decoders, database
cursors, linked-information queries, and remote event streams.

A library can expose a fallible `next()` method and require a manual loop.
Integration with `for` and Luce's explicit propagation rules requires language
lowering.

### The semantic requirement

Retain the current infallible iteration protocol and introduce a distinct
fallible protocol. The loop site explicitly requests propagation, conceptually:

```luce
try for entry in directory.entries():
    process(entry)
```

The spelling remains open. Required semantics are:

- ordinary `for` consumes infallible iteration;
- fallible iteration exposes item, end, and error distinctly;
- propagation is visible at the loop site;
- the loop body retains ordinary `break`, `continue`, `return`, and `defer`
  behavior;
- cleanup of the iterator occurs on exhaustion, error, early exit, and trap
  containment;
- local recovery uses the ordinary Luce failure model.

### Acceptance gate

Exercise directory, decoder, database-cursor, and remote-query iterators.
Differential tests must cover every combination of item, completion, error,
`break`, `continue`, early return, and cleanup.

## 7. The system execution profile

### The pressure

Isolated workers are the right ordinary concurrency model for applications and
behaviors. Kernel and runtime implementation additionally requires operations
whose meaning belongs to the compiler and backend:

- atomic load, store, exchange, and compare-exchange;
- explicit memory orders and fences;
- volatile device access;
- compiler barriers;
- alignment-sensitive storage;
- interrupt and architecture entry ABIs;
- per-core runtime state;
- selected target intrinsics;
- verification of allocation-free or non-blocking roots.

An ordinary package cannot define the semantics of a memory fence, volatile
load, calling convention, or compiler barrier.

### The semantic requirement

Define a monotonic profile lattice:

```text
behavior-safe  ⊂  application-safe  ⊂  system-safe  ⊂  audited-native
```

- **Behavior-safe** code receives scoped snapshots, capabilities, patches, and
  intents under resource budgets.
- **Application-safe** code uses ordinary Luce services, ARC identity, and
  isolated workers.
- **System-safe** code gains closed atomic, volatile, alignment, and ABI
  facilities with compiler-defined semantics.
- **Audited-native** modules gain raw pointers and architecture-specific escape
  hatches.

Profile changes are visible in product/module metadata, build output, compiler
queries, and audit reports. A package's transitive requirements are included in
its effective profile.

The system surface can look API-shaped:

```luce
let old = counter.fetch_add(1, order: .acquire_release)
system.fence(.sequential)
let status = device_register.load_volatile()
```

The compiler and backend own the memory model behind these calls. Locks, queues,
channels, and synchronization policies remain library abstractions built from
the closed primitives.

### Bootstrap boundary

A small architecture bootstrap in assembly or another host-supported format is
expected. Its role should remain narrow and measured. The scheduler, allocator,
synchronization primitives, interrupt dispatch, and drivers should be
expressible in Luce once the system profile is available.

### Acceptance gate

Build three hard system slices:

1. an allocator or page-table manager;
2. a per-core scheduler queue with interrupt ingress;
3. a device driver using volatile registers and DMA-safe storage.

Test their memory ordering on supported architectures, inspect generated code,
run concurrency stress tests, and measure the audited-native surface. Expansion
of raw modules signals a missing system-safe primitive.

## 8. Flow-sensitive refinement

### The requirement

The semantic analyzer should accumulate facts produced by ordinary control
flow:

```luce
if index < items.length:
    let item = items[index]
```

Within the branch, the compiler can know the index is in bounds. The same engine
can track:

- optional presence;
- eliminated enum cases;
- nonzero divisors;
- integer ranges;
- definite field initialization;
- owned-value state;
- scoped-region validity;
- branch-local relationships between immutable values.

Mutation, aliasing, unknown calls, and native calls conservatively invalidate
the facts they may affect.

### Why this belongs in the compiler

A library can perform a runtime check and return an optional or fallible result.
It cannot teach the compiler that a preceding ordinary condition proves a later
operation safe. This analysis improves diagnostics and permits redundant checks
to disappear during optimization. Users continue writing ordinary Luce code.

### Acceptance gate

Add positive, negative, mutation-invalidation, aliasing, and native-call cases
to the semantic test suite. Every removed runtime check must have an explicit
proof fact in analyzed HIR or MIR and must retain differential behavior under
optimization.

## 9. Checked profiles and operational contracts

### The pressure

Several execution environments require transitive guarantees:

- an interrupt handler must obey its allocation and blocking policy;
- a real-time callback has a latency and allocation budget;
- a retryable behavior produces candidate state and declared intents;
- a merge function is deterministic, bounded, and authority-free;
- behavior-safe code reaches host services through explicit capabilities;
- a worker transfer reports its exact copy or ownership cost.

These facts cannot be inferred soundly through arbitrary foreign calls. Native
declarations and generated wrappers must supply conservative contracts.

### The semantic requirement

The compiler computes a closed operational summary for each callable. Initial
facts may include:

- allocates;
- blocks;
- calls native code;
- reads clock or randomness;
- accesses an external service;
- may perform volatile or atomic operations;
- deterministic under recorded inputs;
- suitable for retry within the behavior protocol.

Products and selected entrypoints request constraints. The compiler verifies
their complete reachable call graph, including interface requirements and
foreign declarations.

This design keeps capabilities as explicit values and avoids a general
effect-polymorphic type system. Operational facts become compiler metadata,
profile checks, diagnostics, and descriptor output. Source modifiers can be
considered only for contracts that authors must promise or that participate in
function types.

### Acceptance gate

Verify an interrupt root, real-time callback, deterministic merger, and
retryable behavior. Seed forbidden calls behind helpers, closures, interfaces,
generic instantiations, and foreign wrappers. Diagnostics must print the exact
call path that violates the requested profile.

## 10. Canonical declaration and type descriptors

### The pressure

One semantic operation should support source calls, forms, contextual actions,
graph nodes, commands, scheduled jobs, AI tools, documentation, and compatibility
analysis. Those projections need compiler-owned facts:

- canonical operation identity;
- parameter names, types, defaults, and documentation;
- result and failure shape;
- public struct fields and enum cases;
- generic instantiations and constraints;
- sendability and ownership qualities;
- execution profile and operational summary;
- source and compatibility identity.

Runtime reflection is absent by design, so an ordinary package cannot enumerate
arbitrary declarations or recover erased argument labels from function values.

### The compiler product

Provide a stable, versioned query and artifact, conceptually:

```text
luce describe package.module.operation
```

The output should be deterministic structured data suitable for first-party and
third-party tools. It contains compiler facts and references a separately
declared human semantic contract for:

- labels and explanations;
- reversibility and idempotency;
- confirmation policy;
- privacy and disclosure meaning;
- expected cost and duration;
- domain-specific presentation.

This starts as a compiler service and artifact. Runtime reflection, arbitrary
annotations, code-generating macros, and package compiler plugins remain outside
the mechanism.

### Durable schema identity

Persisted information eventually needs stable field, case, entity, and revision
identities across renames and code evolution. The first vertical descriptors
should determine whether these identities belong in:

- explicit platform schema declarations;
- source-level schema markers;
- compatibility and migration artifacts;
- a combination of these layers.

The language can reserve design space while the experiments determine the
smallest coherent source feature.

### Acceptance gate

Describe one family-film behavior and two unrelated behaviors. Generate their
source API, form, graph node, command, AI-tool contract, documentation, and
compatibility report from the same compiler artifact plus human semantic
contract. Every projection must preserve identity, type, authority, failure,
and provenance.

## 11. Responsibilities that remain above the language

The following concepts remain platform types, protocols, and services:

- snapshots, patches, and intents;
- behavior scheduling and retry;
- capability creation, attenuation, and revocation;
- provenance and commit records;
- synchronization and federation;
- conflict resolution and merge policy;
- AI context construction;
- visual graphs, forms, and conversational authoring;
- persistent collection implementations;
- serialization formats;
- domain schemas and migrations;
- structured task combinators such as `wait_all`;
- sensitivity labels and declassification policy.

The compiler may verify their use at trusted boundaries. Their domain semantics
remain versioned platform responsibilities.

## 12. Ideas that remain in the research queue

The identified gaps do not currently require:

- a pervasive transactional heap;
- shared mutable object graphs between ordinary workers;
- a general borrow checker with named lifetimes;
- universal move syntax for every value;
- general effect polymorphism;
- dependent-type or proof-term syntax;
- runtime reflection;
- procedural or textual macros;
- package-defined grammar;
- implicit distributed calls;
- universal automatic conflict merging;
- `async`/`await` language coloring.

Vertical slices can promote an idea from this queue when they expose a repeated
safety or expressiveness gap.

## 13. Recommended roadmap amendment

The current compiler plan implements the already-designed surface in a long
vertical sequence. The new decisions should enter at the points where later
revision would be most expensive.

### Before classes and ARC

1. Specify owned-value state transitions.
2. Specify consuming calls, results, and destruction.
3. Resolve interaction with failure, closures, fields, interfaces, and native
   ownership.
4. Run the resource corpus before selecting final syntax.

### Before closures and mutable slices

1. Define lexical scoped-value origins.
2. Implement storage, return, capture, interface, and worker escape checks.
3. Re-express `mutable_slice` and structured tasks through the shared analysis.

### Before generics

1. Define permitted constant parameter kinds and expressions.
2. Extend type identity, inference, substitution, artifacts, and
   monomorphization budgets.
3. Build fixed-storage and numerical corpus examples.

### Before `for`

1. Define the fallible iterator protocol.
2. Select explicit loop propagation syntax.
3. Specify cleanup and control-flow interaction.
4. Add exhaustive differential tests.

### When semantic analysis becomes a real stage

1. Track initialization, optional and enum narrowing.
2. Add owned-value state and scoped-region provenance.
3. Add integer and bounds relationships.
4. Define conservative invalidation around mutation and unknown/native calls.

### Before workers

1. Preserve copied sendable graphs as the ordinary transfer model.
2. Add consuming transfer for owned sendable values.
3. Account separately for bytes copied, immutable backing reused, and ownership
   transferred.

### Before native self-hosting and OS services

1. Specify the Luce atomic memory model.
2. Add volatile access, fences, alignment support, and system entry ABIs.
3. Add profile and operational-summary verification.
4. Implement allocator, scheduler, and driver proving slices.

### Before behavior execution

1. Implement behavior-safe product checking.
2. Emit canonical declaration descriptors.
3. Associate human semantic contracts with compiler-known declarations.
4. Validate authority and operational summaries through complete call graphs.

## 14. Proposed 1.0 disposition

Four source-visible concepts should enter the 1.0 design process:

1. opt-in owned/noncopyable values and consuming transfer;
2. generalized scoped values;
3. restricted const generics;
4. explicit fallible iteration.

Four additional capabilities should enter the 1.0 compiler contract:

1. the closed system memory and ABI substrate;
2. flow-sensitive refinement;
3. execution-profile and operational-summary verification;
4. canonical declaration and type descriptors.

ARC remains the ordinary application ownership model. Isolated workers remain
the ordinary concurrency model. Owned values serve exclusive resources,
authority, and transfer. Scoped values serve temporary access. System primitives
remain confined to elevated profiles. Compiler summaries support safety and
projection while source code keeps a compact type system.

## 15. Decision process

Each proposal should pass the existing Luce feature gate:

1. Implement at least three representative corpus examples.
2. Attempt the best library and tooling formulation.
3. Record the safety, clarity, performance, and privilege gaps that remain.
4. Specify the smallest semantic mechanism that closes those gaps.
5. Implement it through parser, HIR, analysis, MIR, verifier, interpreter,
   backends, formatter, diagnostics, and documentation.
6. Add negative programs and differential runtime tests.
7. Measure compilation cost, runtime cost, and conceptual surface.
8. Freeze the feature only after the compiler or an OS vertical slice depends on
   it successfully.

This process lets the larger operating-system vision strengthen Luce's
foundation while preserving the permanent complexity budget.
